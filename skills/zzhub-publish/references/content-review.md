# 内容审核 Brief 构建指南

当 `next_action.action` 为 `review-content` 时审核实际待发布正文。允许且可委派时采用独立审核；否则主 Agent 按相同标准复核。CLI 的 `review` 不会调用模型。

## 构建审核 Brief

主 Agent 构建审核 Brief：读取 `source_body_path`（或 `formatted_body_path`，如果存在）的正文，连同以下审核标准一起交给 sub-agent。

## Spawn Sub-agent

使用当前环境可用的委派工具，提供正文、标题、已确认的用户约束、必要事实来源及审核标准，不带入无关主对话。没有委派能力不阻塞本地复核。

## 审核标准

**写入 sub-agent prompt：**

1. **AI 味检测**：是否读起来像 AI 生成？警惕：过于流畅的过渡句、空洞的总结、无意义的最高级形容词、公式化的结构、缺乏具体细节或个人声音。
2. **标题准确性**：是否准确概括正文，符合用户指定用途和文风，是否夸大效果或编造冲突？不以点击率要求否决正常的说明性标题。
3. **符合原需求**：内容、结构、作者声音和改写范围是否符合约定？新闻以可核验事实为主，操作说明允许顺序步骤，不强制故事或情绪曲线。
4. **事实准确性**：文章中的说法、日期、人名、技术细节是否准确？标记任何看起来有问题的内容。
5. **目标适配**：微信稿是否包含无法导出的组件？博客稿按目标站点能力检查，不将微信限制套到所有目标。字数按用户要求，不自行规定统一范围。
6. **Markdown 结构**：已使用的标题、列表、引用和强调是否正确，是否重复插入标题？不强制每篇使用标题、粗体或特定卡片。
7. **Milkdown 扩展语法合规（参考 [milkdown-writing](../../milkdown-writing/SKILL.md)）**：
   - 导读 `[!INTRO]` 与文末 `[!CTA]` 卡片内部每行是否均保持 `>` 引用标记？多段之间是否使用 `>` 空行（避免被普通空行截断为多块）？
   - 提示块（`[!NOTE]`、`[!TIP]` 等）是否使用规范标识？
   - 是否避免了微信不支持的组件（LaTeX 公式、Mermaid 图表、折叠详情块、文内锚点）？
   - 正文是否混入 `封面高亮关键词`、审核结论、CLI 指令等交稿元信息？这些内容应移除；封面词单独交给 `prepare`。

## 交稿流程

Sub-agent 返回审核结论（passed / needs_revision）和具体反馈。

主 Agent 根据 sub-agent 返回的结论执行：

- **通过** → 执行：
```bash
zzp review --state "{state_path}" --status passed
```

- **需要修改** → 执行：
```bash
zzp review --state "{state_path}" --status needs_revision --feedback "具体修改建议..."
```

反馈必须具体可操作，用中文写，明确指出段落与问题。每次记录后重新 `status --view agent`；用户明确批准并采用 `trust_user` 的正文不额外制造审核循环。
