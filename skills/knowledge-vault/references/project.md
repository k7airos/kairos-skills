# 项目知识沉淀

沉淀或更新某个项目的知识时使用。项目知识分三层，按任务需要渐进读取，避免架构内容白占上下文。

## 三层结构

```text
knowledge/
└── projects/
    └── <project-id>/              # 项目 ID：<vault前缀>.project.<slug>
        ├── PROJECT.md             # 项目卡：入口，进项目必读
        ├── business/              # 业务层：产品规格的简化版
        │   └── <module>.md
        └── architecture/          # 架构层：给 AI 写计划、动手前读
            └── <module>.md
```

- 项目在 `INDEX.md` 用项目 ID、一句话摘要和项目卡路径路由；索引也可包含复用资产和知识主题，不为普通模块增加重复条目。TODO是独立工作入口。
- 项目 ID 必须带所选 Vault 前缀，如 `<vault-id>.project.<slug>`。
- 模块名用稳定短标识（如 `user-auth`、`order-flow`）；业务页与架构页同名配对。

## 渐进读取规则

1. 找某项目的一般信息：`INDEX.md` → `PROJECT.md`，到此为止。
2. 问题涉及行为、流程、业务规则、权限：再读 `business/<module>.md`。
3. 要改代码、动架构、写实施计划：才读 `architecture/<module>.md`。

不预读架构层；一次任务只读触及的模块页。找"某项目用户管理里超管权限"的路径固定为：INDEX → 项目卡 → user 模块业务页/架构页。

## 项目卡 PROJECT.md

每个项目一页，永远先读它。至少包含：

- 项目名、项目 ID、一句话定位。
- 给谁用：真实用户/角色，使用场景。
- 技术栈：语言、框架、关键依赖（醒目，跨项目找复用时靠它）。
- 仓库标识、位置和启动/运行入口；公共知识优先用仓库URL及可移植路径，本机绝对路径只放本地映射或允许记录它的私有库。
- 模块清单：每个模块一行摘要 + 业务页/架构页链接；无页面的模块注明"未沉淀"。
- 全局配置入口：配置文件路径或配置中心位置，链接到业务页全局配置节。
- 复用资产：共享组件、品牌资产、交互模板的位置（个人项目重点字段）。
- 架构基线：pinned commit（见下）。
- 敏感边界：哪些配置/密钥只记受控引用，不落值。

## 业务页 business/&lt;module&gt;.md

贴近真实用户需求的简化产品规格，写：

- 功能点清单：这个模块提供什么能力。
- 角色与权限：谁能用、能做什么、不能做什么。
- 主流程：正常路径一步一步怎么走。
- 分支与异常流：分叉条件、校验失败、边界情况。
- 业务规则与状态机：关键实体的状态、转换条件、谁触发。
- 全局配置项（业务含义层面）：有哪些开关，分别影响什么行为。
- 术语表：模块内有特定含义的词。

不写：按钮、表头、页面布局等 UI 细节；具体代码实现；接口字段级罗列（除非字段语义本身就是业务规则）。

## 架构页 architecture/&lt;module&gt;.md

给 AI 读完后写计划或直接动手用的，写高层次设计而非实现：

- 模块边界与职责：它管什么、不管什么。
- 依赖关系：依赖哪些模块/服务，被谁依赖。
- 数据流向：数据从哪来、经过哪些组件、落在哪、被谁消费。
- 核心抽象与复用点：关键的类/服务/机制设计，为什么这样分层。
- 动态配置项：key、默认值、作用范围、读取时机、改了影响什么。
- 关键决策与原因：为什么这么实现，否决过什么方案（知道才写，标注来源）。
- 权限模型实现方式（公司项目必填）：权限在哪一层判定、怎么落地。

硬规则：

1. **每条架构论断必须带代码锚点**，格式为 `仓库相对路径::符号名`（类、函数、模块名），不用行号——行号会漂移，符号名可 grep。
2. 页头 frontmatter 记录 `pinned_commit`。使用架构页前先 drift check：

   ```bash
   git -C <repo> diff --name-only <pinned_commit>..HEAD -- <被引用的文件...>
   git -C <repo> status --short -- <被引用的文件...>
   ```

   任一有输出说明锚点或当前工作区可能不同，先核验相关内容。只有对应稳定提交的已核验结论才能更新页头commit，不能把在途修改归到旧HEAD。
3. 未提交实现不能进正式知识，放TODO/handoff记录当时进度和验证边界；需要保留待核验结论时建Inbox候选。
4. 不贴大段代码、不逐函数罗列实现；写综合结论，锚点负责定位。
5. “当前实现”以代码和运行证据为准，“期望行为”以获确认的需求/决定为准；两者不同时分别记录，不用代码否定已确认的后续方向。

## 个人与公司 Vault 的差异

差异体现在 Vault 级别，不搞两套结构：

| | 个人 Vault | 公司 Vault |
|---|---|---|
| 项目形态 | 多而杂，技术栈不一 | 数量少，业务复杂，多人协作 |
| 项目卡 | 技术栈、复用资产字段必填且醒目 | 同样必填，另加敏感边界 |
| 业务页 | 要点可内联在 PROJECT.md，模块页按需拆 | 核心模块必须齐备 |
| 架构页 | 可选；只给复用性高、交互复杂、品牌资产相关的模块写 | 核心模块必须齐备 |
| 事实标准 | 代码为准 | 代码为准；PRD、需求单、会议结论只作来源，冲突并列 |
| 必填重点 | 复用性、页面交互、品牌资产 | 权限模型、状态机、决策原因 |
| drift check | 建议执行 | 必须执行 |

## 项目沉淀流程

1. 先读项目卡；新建或更新须满足Vault写入策略。代码页固定实际核验的稳定commit；跨项目决定等非代码页可注明不适用，不伪造Git来源。
2. 分阶段沉淀：来源齐全、目标唯一、无冲突时按 [write.md](write.md) 与promotion_policy直接更新正式页；存疑事实留候选，在途进度留 [TODO/handoff](tasks.md)，不等整个项目完成。
3. 更新已有页先检查相关源码漂移，只核验和更新本次涉及范围，写前检查并发变化、写后回读；一次变更记一条日志并按 [Git策略](git.md) 提交。
4. 跨模块共享的全局配置、整体数据流向写在 PROJECT.md 或 `architecture/global.md`，模块页只链接、不重复。
5. Skill改进遵守write.md的授权边界，普通知识维护不顺手修改公共协议；公开Skill与私有知识分别提交。
